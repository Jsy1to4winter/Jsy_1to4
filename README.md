# V19 个人主页 · Supabase 完整同步版

基于提供的 V19 HTML 继续修改，保留布局、视觉样式、邮箱/密码管理员登录、音乐播放器、相册与图片放大预览。纯静态项目，无需构建，可直接部署 GitHub Pages。

## 一次性配置 Supabase

1. 先备份现有 `homepage_profiles` 数据及相关策略。在 Supabase SQL Editor 执行 [supabase/setup.sql](supabase/setup.sql)。该脚本创建/配置 `homepage-media` 公共桶、主页和 Storage 的 RLS、服务端更新时间戳，并保留已有 `fuguang` 资料及 `owner_id`。若表/记录不存在，把脚本的 `YOUR_ADMIN_EMAIL` 改为已有 Auth 管理员邮箱。不要把密码或密钥写入 SQL 文件。
2. 确认 `homepage_profiles` 中 `slug=fuguang` 的 `owner_id` 为你管理员在 Authentication → Users 中的 UUID。如果已有表缺少 `owner_id`、`profile_data`、`updated_at` 或 `slug` 唯一约束，需先核对旧表结构再迁移，不能盲目清表。
3. 保留原管理员邮箱/密码登录。此网站没有注册入口；建议在 Supabase Authentication 中关闭不需要的公开注册。其他已登录用户也不具备此主页的编辑权。
4. `index.html` 的 `supabase-config` 使用项目 URL 和 **Publishable Key**（允许公开）。代码不需要 Secret Key / `service_role` Key。换项目时只更改 URL、公开 Key 及 slug，并在 SQL 中对应修改 slug。
5. 项目网络需允许 `nedsvrzbsrethlyyoqey.supabase.co` 和 `cdn.jsdelivr.net`。Storage 是公共桶，只上传本来就要公开的图片和音乐。

## 部署 GitHub Pages

把此项目文件放在仓库根目录，至少包含 `index.html` 和 `cloud-sync.js`，两者应同时更新。GitHub → Settings → Pages → Deploy from a branch → `main` / `(root)` → Save。等待部署完成后打开 Pages 地址。无需 npm install、打包或后端服务器。

本地预览：

```sh
cd /workspace/Jsy_1to4
python -m http.server 8000 --bind 0.0.0.0
```

使用 HTTP 访问进行测试，不要直接双击 `file://` 文件。

## 使用与旧数据迁移

- 右上角锁图标用原管理员邮箱、密码登录。前端确认当前 Auth 用户等于主页 `owner_id`，数据库和 Storage 另行强制验证权限。访客只能浏览。
- 保存昵称、个人简介、标签、统计、邮箱、卡片和三个板块前言，会统一写入 `profile_data`；“关于我”和留言有各自保存按钮。保存成功提示只在云端确认后出现，网络错误保留编辑窗口。
- 相册、主页头像、关于我图片、单条留言头像和 MP3 上传到 Storage，数据库保存公开 URL。删除或替换资料时先提交数据库，再删除不再被引用的文件，避免写入失败后破坏公开页面。单个文件最多 50 MB，每板块相册最多 6 张。
- 管理工具可删除主页头像、关于我图片和音乐；删除留言或替换留言头像后，原头像在无其他引用时会清理。取消留言编辑不上传头像。
- **原浏览器有尚未同步的文字时**：先在编辑主页工具中使用“备份旧浏览器文字”，再“导入旧浏览器文字”。该操作明确用原浏览器文字、关于我、板块前言和留言替换云端内容；不要在新浏览器误用。
- **原浏览器有本地相册/音乐时**：点“上传旧浏览器媒体”。会迁移 IndexedDB 文件，跳过已迁移项目；云端已有音乐时保留云端音乐，已有头像/关于我图片也保留云端。不要在迁移前清除原浏览器数据；旧站和新站必须使用相同域名及浏览器来源才能访问原存储。若换域名，先在旧域名部署本版并迁移。
- “导出资料”导出完整 JSON（包含文字、留言和媒体 URL）；“导入资料”兼容旧版个人资料 JSON 和新版完整 JSON。备份中的 URL 依赖对应 Storage 文件仍存在，不能当作媒体离线备份。
- 保留“导出访客版 HTML”功能：这是当时资料的只读快照，不自动更新。持续同步的公开站点必须部署完整项目，而非该快照。

## 同步及失败行为

云端是展示资料的事实来源。新设备打开页面会读取最新数据，页面重新获得焦点且没有编辑窗口时也会刷新。不会用空的新浏览器本地存储覆盖云端。

保存使用 `updated_at` 作并发条件，SQL 触发器为每次修改设置服务端时间。另一设备已修改时，本次保存拒绝覆盖；先导出/复制未保存输入，再点击“重新读取云端”，重新编辑并保存。读取失败时禁止写入。上传后数据库保存失败，会尝试删除本次上传的无引用文件；若网络故障同时阻止清理，需在 Storage 后台核对并清理孤立文件。资料已保存但旧文件清理失败时，会单独提示。

公开媒体文件不保证立即从浏览器/CDN 缓存消失；数据库中已删除的文件不会再被主页引用。

## 验证状态及上线验收

已运行真实 Supabase JS SDK 配合模拟 HTTP 的 Chromium 功能测试，以及在嵌入式 PostgreSQL 中执行实际 SQL 的权限测试。见 [tests/README.md](tests/README.md)。这两类测试不代替真实项目的端到端验证。

初次验证时访问实际 Supabase 被网络代理返回 **CONNECT 403**。后续排查已可匿名读取真实主页（HTTP 200），并确认 `homepage-media` 尚不存在（Storage 返回 `Bucket not found`）。已有内嵌头像现在会保留在数据库中，不再因保存文字而强制上传；新增媒体及显式迁移仍须先执行 SQL 创建桶及策略。没有登录真实账号、执行项目 SQL 或确认真实云端写入。上线前务必：

1. 执行 SQL，确认原有管理员仍可登录，编辑并保存所有文字板块。
2. 上传/替换/删除相册、头像、留言头像和 MP3，在 Storage 和 `profile_data` 核对引用；用播放器实际试听音乐。
3. 用另一设备或无痕窗口访问 Pages，确认最新文字、图片、音乐及留言可读。
4. 在未登录和非 owner 的已登录账号下，直接调用数据库及 Storage 写入接口，确认被拒绝。匿名读取应成功。不要只凭编辑按钮隐藏就判断 RLS 安全。
5. 用两个设备同时编辑，确认后保存的一方收到冲突提示，而非覆盖前一设备的修改。

SQL 中限制性策略会约束本表/桶已有的宽松策略，但项目中其他自定义 RPC、触发器和安全定义者函数仍需按实际数据库审查。
